# Independent Assurance checklist for the TRUST 1.2 runtime link

Status: prepared template. This checklist has not been executed. It becomes usable only after
every runtime-link cell, the malformed branch of each profile and the central closure artifact
exist and a seal with status `SEALED_FOR_INDEPENDENT_ASSURANCE` has been produced from them.

The checklist implements the four independent checks of the central refinement closure. The
frozen inputs, reproduction commands and reuse conditions are defined by
[the seal specification](assurance-input-seal-spec-v1.json) and validated against
[the seal schema](assurance-input-seal-schema-v1.json).

## Who may run it

1. The assessor has not taken part in any Building session of this runtime link and does not
   reuse an agent, a transcript or a conclusion of one.
2. The assessor reads only the sealed inputs. Handoffs, status summaries and chat reports are
   not inputs.
3. The assessor never edits a sealed file. Any change returns the work to Building and needs a
   new seal.

## Before the checks

1. Verify the seal against the bound roots and record the output:

   ```
   python3 scripts/trust12/tail-preparation/assurance_seal.py verify --seal SEAL --root PRODUCT=PRODUCT_CHECKOUT --root EVIDENCE=EVIDENCE_ROOT --root MAINTAINER=MAINTAINER_TOOLS --root VERI=VERI_ROOT --root AFP=AFP_ENTRY
   ```

   `MAINTAINER_TOOLS` is the maintainer tool directory that holds the process policy which the
   recorded kernel runs read. `VERI_ROOT` and `AFP_ENTRY` are the Veri formal root and the AFP
   entry that the recorded kernel catalog loads. Verification rechecks every file that a sealed
   input list names against that list. `PRODUCT_CHECKOUT` is a clean checkout of the sealed
   commit in a directory of its own; it is never the clone that holds the evidence root.

2. Confirm that the seal status is `SEALED_FOR_INDEPENDENT_ASSURANCE`. A `TEMPLATE_DRY_RUN`
   seal ends the Assurance with the result "not started".
3. Install the toolchain exactly as pinned by the seal. Record the observed versions next to the
   pinned ones.
4. Select the declared replay scope before sealing and running the checks. This specification
   describes current-completion Assurance: verify every sealed result and native freshness,
   replay changed units and their affected consumers, and replay gate checks and selected
   top-level kernel consumers. The public product proof sessions still receive a clean replay.
   Each reused unit must satisfy all five reuse conditions of the seal. For a final frozen-source
   clean Assurance, prepare a separate specification and seal with `coldReplay: true` for
   `runtime-link-kernel-replay` and a command that executes every sealed kernel run without
   recorded heaps. Do not relabel or edit a current-completion seal as a final clean seal.
   Both scopes reuse the proof sources and tools; neither requires rebuilding the proof method
   from scratch. The final specification is
   [assurance-input-seal-spec-final-v1.json](assurance-input-seal-spec-final-v1.json). Both
   scopes run the kernel replay from the same sealed kernel replay kit: the current-completion
   specification in its top mode and the final specification in its cold mode. The independent
   Assurance that closes the conditions list of this runtime link uses this current-completion
   specification; the final specification and its cold replay are optional for that closure.
5. Regenerate every sealed input list from its recorded generator and require it to be
   byte-identical, so that a file a recomputation newly reads, or no longer reads, is detected:

   ```
   python3 scripts/trust12/tail-preparation/assurance_inputs.py check --list EVIDENCE_ROOT/LIST_PATH --root PRODUCT=PRODUCT_CHECKOUT --root EVIDENCE=EVIDENCE_ROOT --root MAINTAINER=MAINTAINER_TOOLS --root VERI=VERI_ROOT --root AFP=AFP_ENTRY
   ```

   The kernel replay kit list is not regenerated by this tool; the kernel replay preflight checks
   it file by file.

## Kernel replay

The sealed kernel replay kit holds a manifest of the recorded chain (every session with its
recorded heap, its recorded session database and the fingerprint of that database), the recorded
catalog, the recorded build command with placeholders for the run paths, the process policy and
the replay tools. The kit tools are run from the sealed kit directory, and every long step is
launched through `start_detached.ps1` so that it outlives the calling shell. While a replay runs,
no other prover, Foundry, Kontrol or WSL process runs on the host; the Foundry-based checks of
Check 3 run before or after the replay.

Heap bytes and database bytes are not compared: two builds of the same sources write different
Poly/ML heaps and different timing records. The normalized messages carry every theorem statement
that the build printed and every audit marker, so equal messages and equal sources show that the
same statements were proved again.

### Top-session replay (current-completion Assurance)

The run store starts as a copy of every recorded heap and session database of the manifest, and
only the declared replay groups are removed from the copy and rebuilt from the sealed sources over
the copied ancestor heaps. The recorded stores are only read.

| Step | Action | Pass when |
| --- | --- | --- |
| 1 | `run_kernel_replay.py cells`: list the cell sessions of the sealed ledger, and choose one per profile | The choice is recorded before step 2 |
| 2 | `run_kernel_replay.py preflight --mode top` with the declared replay groups: check the kit as in the cold mode, then copy every recorded heap and session database, hashing each file while it is copied | `PASS_TOP_REPLAY_PREFLIGHT`: every copied file equals the size and SHA-256 of the manifest |
| 3 | `start_detached.ps1 -Mode fresh`: run the build command with `-n` over the full copy | `PASS_TOP_REPLAY_FRESH`: exit code 0, no session to build and the copy unchanged, so every recorded result is current for the sealed sources, options and parent heaps |
| 4 | `start_detached.ps1 -Mode start`: for each replay group, highest in the chain first, remove its copies and build its top sessions; after an interruption, `-Mode resume` continues with the group that did not complete | `PASS_TOP_REPLAY_BUILD_COMPLETED`: each group builds exactly its sessions, every rebuilt heap and database is created by the run, and every other copy still equals the manifest |
| 5 | `compare_kernel_replay.py --run`: recompute the recorded fingerprint of every rebuilt session from its recorded database, then compare the rebuilt database with it | `PASS_TOP_REPLAY_REPRODUCED`: the same criteria as step 4 of the cold replay |

A replay group must contain every session between each of its sessions and its top sessions, and
no group may contain an ancestor of a session of a group that is rebuilt later; the runner refuses
a selection that breaks either rule, because Isabelle would otherwise rebuild sessions outside the
group.

### Cold replay (final frozen-source clean Assurance)

The cold replay rebuilds every kernel session that the sealed kernel replay manifest names in a
heap store and a system heap directory that both start empty: the parent chain of the final
target, from Pure and HOL of the pinned Isabelle distribution upward, and every further session
whose recorded result a sealed record cites. It uses the sealed catalog, build options and process
policy of the final chain, and it reads no recorded heap, database or proof object. The recorded
databases are only the comparison baseline.

| Step | Action | Pass when |
| --- | --- | --- |
| 1 | `run_kernel_replay.py preflight --mode cold`: check every file of the kit input list, the tools, the process policy, the Isabelle launcher and user settings, the free disk and memory, and that no prover process and no WSL virtual machine runs | Status `PASS_COLD_REPLAY_PREFLIGHT` |
| 2 | `start_detached.ps1 -Mode plan`: run the build command with `-n` in the empty store | The sessions Isabelle would build equal the expected sessions of the manifest exactly |
| 3 | `start_detached.ps1 -Mode start`: run the build detached; after an interruption, `-Mode resume` continues in the same run directory and store | Exit code 0, every expected session finished, no other session built, every heap and database of the store created during the run and the system heap directory still empty (`PASS_COLD_REPLAY_BUILD_COMPLETED`) |
| 4 | `compare_kernel_replay.py --run`: compare the fingerprint of every rebuilt session database with its recorded fingerprint | `PASS_COLD_REPLAY_REPRODUCED`: return code 0, no recorded error, the same sources digest, ancestor names, export inventory, theory exports and normalized messages, no nonzero oracle count, and a database uuid that differs from the recorded one |
| 5 | `compare_kernel_replay.py --baseline-only`: recompute every recorded fingerprint from its recorded database after checking the database size and SHA-256 | `PASS_COLD_REPLAY_BASELINE_RECOMPUTED` |

The runner builds Pure first, alone and without the recorded process policy, because Pure has no
parent heap and the policy starts only a process that loads exactly one parent hierarchy; the
process policy is not a content option and enters no sources digest. Every other session is built
by the recorded command.

## Check 3: removal negatives

| Step | Action | Pass when |
| --- | --- | --- |
| 3.1 | Reproduce every certificate-removal and consumer-removal negative cited by the ledger, within the replay scope of the seal as stated below the table | Each negative fails at the claimed consumer |
| 3.2 | Rerun the declared mutation campaign and the semantic consumer removals | Every declared fault is killed by its declared detector |
| 3.3 | For each profile, disable one malformed guard at a time and rerun the malformed probe | The probe fails for every disabled guard |

In a current-completion Assurance, a kernel negative of step 3.1 inside a replay group is rebuilt
and compared by the top-session replay, and every other kernel negative is a reused kernel result
that the copy check, the no-build run and its recorded result cover under the five reuse
conditions. In a final clean Assurance, the kernel negatives are rebuilt and compared by the cold
kernel replay. In both, the negative outside the kernel is rechecked from its sealed record and the
product mutation it is bound to. Step 3.2 runs `scripts/run-mutations.ps1` on the sealed checkout.
Step 3.3 runs the declared length guard mutants with `run_malformed_probe_v2.py`, the declared
bounded word guard mutants with `run_word_guard_probe.py` and the declared typed failure mutants
with `run_typed_failure_probe.py`, each on an isolated copy of the sealed checkout.

## Result record

The assessor writes one result document next to the seal, never inside it, with:

1. the seal root hash and the verification output of the seal before and after the checks;
2. the observed toolchain versions;
3. for every step above, the command, exit code, elapsed time, output hash and verdict;
4. the list of reused units with the evidence for each of the five reuse conditions;
5. a final verdict of PASS, or RETURN TO BUILDING with the failing steps;
6. for the Assurance that closes the independent Assurance condition of the conditions list, a
   machine-readable report with schema `trust12-final-assurance-v1` in the assurance directory
   of the TRUST 1.2 evidence, next to the seal: `status` `PASS_FRESH_ASSURANCE` only when the
   verdict is PASS, `independentOfBuilding` true, the `reviewer`, the `seal` path and SHA-256,
   the replay scope of the seal, `reproduction.status` PASS only when every reproduction entry of
   the seal passes, including its kernel replay, `consumerRemoval.status` PASS only when every
   step of Check 3 passes, and `finalIdentities` computed by the release policy from the sealed
   commit and the seal.

A PASS verdict supports only the exact scope that the sealed central artifact names. It does not
extend to compiler correctness, deployment identity or external dependency behavior unless the
seal contains a separate closure for them.
